# Batch 12: student event notifications

Attendance, result publication and receipt issuance now enqueue email notices inside the source transaction. The source change, notification jobs and audit entry commit together. Provider calls remain outside these transactions in the separate notification worker. No additional package or migration is needed for this batch; the notification-delivery migration from batch eleven must already be applied.

Recipients come only from active parent profiles linked to the active student in that school. Valid email addresses are trimmed, lowercased and deduplicated per student event. Cross-school links are excluded even if inconsistent legacy data exists. Student parentEmail fields, provider payer metadata and unrelated contacts are not used as fallback recipients. Parent profiles do not need a portal login to receive mail when the school has linked the profile to the child.

Attendance notices cover ABSENT and LATE through class marking, single-record updates and offline sync. Retrying an unchanged status does not enqueue another notice. Correcting the status cancels pending notices for the old state; a later real status change can generate a new notice. Multiple changes to one record within an offline batch notify only about its final committed state. Notes are omitted from email. Attendance notices expire two days after queueing; the body identifies the actual attendance date, including delayed offline entries. Invalid calendar dates and foreign or duplicate class exceptions are rejected.

Both single-result transitions and class/term publication enqueue notices, with repeated publication treated as a retry. Notices identify the student and term without including scores or grades. Unpublication cancels pending publication notices, and a later publication generates a new event. Publishing permissions and source state are rechecked inside the school transaction.

Each newly issued receipt queues a notice about the amount allocated to that child's invoice. This covers manual payments created with allocations, later allocations and verified Paystack finalization. Duplicate payment requests or provider callbacks do not create another receipt notice. Unallocated payments have no child/invoice recipient and send nothing until allocation. Manual reversal cancels pending notices for its voided receipts. No second full-payment notice is sent alongside each receipt.

The delivery worker rechecks that the recipient is still linked to the child and that the source remains valid: matching attendance status, current published result, or unvoided receipt backed by a successful payment. Stale jobs are cancelled. A message already accepted by a provider cannot be recalled; SMTP still has the at-least-once limitation described in NOTIFICATION_DELIVERY_FIX_GUIDE.md.

Build and restart the API and notification worker to use the new hooks. With EMAIL_PROVIDER=disabled, events are still queued and expire normally when an enabled worker processes them. Review pending mail and confirm staging recipient data before enabling delivery. This task does not send live email, start the worker or backfill historical events.
