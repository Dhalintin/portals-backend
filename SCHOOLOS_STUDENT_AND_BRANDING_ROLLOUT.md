# SchoolOs branding, family payments and student access

## Deploy / run locally

No new web or backend dependency is required. The supplied logos are used directly; the existing licensed Plus Jakarta font is also served locally for result printing.

1. From portals-backend, point your environment at the intended database and run `npx prisma migrate deploy`.
2. Run `npm run build`, then restart/deploy the backend (the existing local dev command watches dist).
3. From portals-frontend run `npm run build` and deploy/restart the frontend.
4. Existing PWA users should open online once and download their workspace again so the new student pages, report documents, font and logos are available offline.

Migrations: `20261101170000_student_portal` adds student accounts; `20261101210000_student_activation` makes every active student eligible to register by default, with a private activation-code hash and expiry. Previously disabled student accounts stay disabled. No predictable/default password is assigned. Apply both migrations before running the updated backend. No shared database was migrated during implementation.

## School administrator: provide student access

- Students → select a class (or Without a class) → row action menu → Student access.
- Select New student: get activation code → Create activation code.
- Copy and share the admission number, school-specific link and code privately with the student or parent.
- Codes expire after seven days, can be used once, and are shown only when issued. Issuing another code replaces the previous one.
- The student opens the link, enters their admission number and code, and chooses a password. This creates their account and signs them in.
- Existing students with accounts continue signing in normally. Use Reset password for forgotten passwords or to restore previously disabled account access; it revokes old online sessions.
- Disable student access also invalidates any unused activation code and blocks online access. Only users with students:write can issue/reset/disable credentials.
- Registration requires the private code: admission number alone never grants access. Activation and password changes require an online connection.

## Simplified student upload

- Optionally select a class, choose an Excel/CSV file, then confirm the automatically checked preview. There is no separate validation button in the successful flow (two app actions, or three with class selection; the system file-picker selection is additional).
- Only firstName and lastName columns are required. Admission numbers, className/classArm and contact details are optional.
- Students without a class remain in Without a class. Missing admission numbers are generated by the backend; existing supplied admission numbers are checked for duplicates.
- A current school year is not required. When available, class-assigned rows get enrollment records; unassigned rows do not.
- Repeating a saved upload uses its original idempotency key, so a network retry does not duplicate students. A new upload containing only names cannot identify the same person reliably; include admission numbers when reusing a file.
- Student import remains a live, validated operation rather than an offline queued bulk creation.

## Attendance and interface density

Present and Absent are the main choices. Track lateness is optional; saved late marks stay visible. Excused absence is available only after marking someone absent. Summary totals include late arrivals as present and excused absences as absent; optional details appear only when used. The absent-today report excludes late arrivals.

Dashboard content spacing is another 8% smaller, with slightly smaller headings and stat numbers. Text remains readable and controls retain a 44px minimum target. Landing and login/registration sizes are unchanged. Scrollbars remain functional but thin and school coloured; the sidebar scrollbar stays hidden. Student menus and confirmation dialogs render outside table clipping containers.

The landing page now uses the existing classroom illustration and visual feature previews. Each feature has a plain heading and no more than two short sentences; all example data is labelled illustrative.

Admission numbers are unique within each school, not globally. School-specific sign-in links supply that context automatically. The central student sign-in page can resolve matching credentials or offer verified school choices; common admission numbers across more than 50 candidate schools require the school-provided link. Families never have to type a school slug.

## Student / simple family access

- Sign in at the school-provided student link with admission number and password.
- Home offers just Results and Fees, with Settings in navigation.
- Results contains only the student's published/released results. Other students' records and draft reports are inaccessible server-side.
- Print / Save result PDF opens the new A4 document: school logo/name, term and session, student identity, class, total/percentage/position, subject scores with the term's marking weights, comments and endorsement lines. Blank endorsements are not electronic signatures.
- Fees shows paid and outstanding totals first, a compact breakdown and separate receipts. Make a payment opens item selection. Choose all or selected unpaid items.
- Students enter a receipt email in the payment flow; it is saved for future payments. It does not grant parent access or change login identity. Payments always require a live connection and the school's existing payment-provider configuration.
- If online checkout is unavailable, the payment panel shows configured bank instructions or tells the user to contact the office. Bank transfers still require school confirmation.
- Settings allows a payment-receipt email, display name, picture and password changes. The school manages the academic record name, admission number and class. Forgotten student passwords are reset by the school office, not through a fabricated email inbox.

## Student requests a parent email update

- Settings → Request a parent link → enter parent's email → Send parent request.
- The draft and queued request stay scoped to that student/account/school. A request never grants access automatically.
- School: Parents and guardians → Student parent requests → verify the relationship against school records → enter the parent's name → approve or decline with an explanation.
- Approval links an existing active parent with that email or creates a parent record. Existing guardians remain linked. Duplicate email records require school cleanup before approval.
- If the parent has no login, use the existing parent directory invitation flow after approval. Approval alone does not send an invitation or create a parent login.
- Student sees pending / approved / declined and the school's explanation. Repeated requests for the same normalized email return the existing request.

## Parent payment redesign

The balance and payment action appear before the breakdown. One-child families are not asked to select the only child. Repeated invoice metadata is hidden when there is one invoice. Item selection and checkout appear only after Make a payment; receipts have their own tab. The existing payment-attempt recovery, provider verification, idempotency and receipt permissions remain in place.

## Branding / marketing

SchoolOs replaces visible Portals naming on public and account screens. The landing page uses navy, green, gold and paper, the supplied mark/wordmarks and the established typography. It describes working results, fee records, attendance, staff/student/parent records, timetables, notices and installed-web-app offline support. It does not advertise PIN sales, completed native apps, fabricated customer counts, testimonials or invented pricing. Dashboard examples are labelled illustrations.

Uploaded school logos remain in use. The SchoolOs mark is a fallback for missing/broken logos in shared navigation/login/report components. Existing PWA PNG icon sizes are retained for installation compatibility; the app name and browser favicon use SchoolOs.

## Google profile details

Verified Google ID-token names and picture fill blank fields during login and invitation acceptance. Existing names and photos are preserved. Email/Google-subject, nonce and audience checks remain mandatory; sign-in does not silently attach unrelated Google accounts.

## Offline / security boundaries

Student pages use the same signed offline view grants, account/school-scoped snapshots and durable outbox as the web/PWA. Published reports and receipt data can be downloaded while connected for later offline viewing/printing. Parent-email requests queue offline. Live credentials, payments, account changes and school review decisions are never optimistically approved. Server authentication and permissions are rechecked during sync. Revoking an online account cannot remotely erase records on a device that remains disconnected.
