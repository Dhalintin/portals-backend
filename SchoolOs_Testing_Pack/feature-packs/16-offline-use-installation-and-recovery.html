Offline use installation and recovery

Follow only the cases assigned to you. Record what actually happens, even if the page is confusing or something goes wrong.

Who tests this: Teacher; bursar; parent; student; coordinator

Before starting: Use a deployed HTTPS production version, or the coordinator's prepared localhost production build. Use only one account/device per offline run and keep work saved.

Your test details

The web address is from the earlier staging setup. Your coordinator must confirm it. Enter only the app home address, never an invitation/reset link.

How to record each test

Passed: what should happen actually happened. Failed: it did not. Cannot test: you lack the account, data, connection or setup. Not tested: you have not tried it.

After a save, reload the app page to check it stayed saved. Test with invented records only. Never put passwords, activation codes, bank codes, card details or private links in this document.

Try without help first. If you need help, say so: that is useful feedback, even when the feature works.

Continue from a saved backup

For another tester or role, download the current report and backup first.

Answers stay in this browser when saving is available. The original checklist file does not contain your answers.

Install the offline web app

16-01

Use: Any supported user

Prepare: An installable production build. Ordinary development mode is not a full offline-install test.

  1. While online, find Download offline version or Install app.
  2. Follow the browser prompt.
  3. Open SchoolOs from its new home-screen/desktop icon.

Should happen: The installed app opens the same permitted school workspace. If installation is unavailable, instructions explain the supported browser path.

Keep working when the school server stops

16-03

Use: Any prepared user

Coordinator required

Prepare: Coordinator handles the test server; tester does not edit settings or run commands.

  1. Keep the device connected to the internet.
  2. Have the coordinator stop only the test backend.
  3. Reload an already prepared protected page.

Should happen: Saved authorised pages still open. An access-check warning does not unnecessarily block records just because the backend is unavailable.
