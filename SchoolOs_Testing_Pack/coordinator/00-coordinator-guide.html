Coordinator guide for the full SchoolOs test

Prepare the school and accounts, assign small feature packets, collect the downloaded reports and arrange retests. These documents are a test plan, not evidence that a feature has already passed.

Do not begin on real school records. Use two disposable schools and controlled inboxes. Keep payments in the provider's test mode. Give passwords and activation codes privately, outside the tracker and test reports.

What to give each tester

  1. The current test app address and their own private sign-in details.
  2. The entire extracted pack, or their assigned feature HTML file. Each feature file works on its own; the link back to the index needs the full folder.
  3. The exact test school, role, class, subject, term and case numbers.
  4. The applicable sample upload files and only the controlled records needed for that task.
  5. A place to return the downloaded completed report, backup and separately named screenshots.

A feature packet is usually best split into a small first sitting of 5 to 8 cases. Repeat essential flows with another tester/device. Do not hand every packet to one non-technical person.

Before the first tester starts

  • Confirm the staging address and deployment version. The earlier supplied frontend was https://portals-frontend-woad.vercel.app/ and backend was https://portals-backend-kyaf.onrender.com. Testers use the frontend, not the backend address.
  • Have the developer apply the current migrations, including student activation, and deploy/restart both apps. Do not ask non-technical testers to run database commands.
  • Create School A for the shared journey, School B for privacy checks, and a separate disposable school/class for uploads and destructive experiments.
  • Use controlled inboxes for invitations, password resets, Google and bank codes. Confirm email delivery before assigning those cases.
  • Confirm whether Google and payment-provider test mode work. Missing configuration means Cannot test, not Passed.
  • Prepare every account in account-allocation.csv. Use a unique account per concurrent tester so profile/password/role changes do not conflict.
  • Record teaching subjects and class-teacher assignments. A job title alone is not a classroom assignment.
  • Prepare the actual phone/desktop browsers. Offline/PWA tests require the production HTTPS app or an approved localhost production build; ordinary development mode is not equivalent.
  • Arrange a coordinator to control test backend outages, permission removal and slow-connection tests. Testers should not use technical tools.

Suggested run order

  1. Confirm deployment, accounts, email and the disposable schools.
  2. Run 01 to 06 for access, school setup, classes, records and family links.
  3. Run 07 to 10 for attendance, scores, release and timetables. Prepare 15/15/70 in a separate clean term; changing an in-use marking scheme should be blocked.
  4. Run 11 then 12 for exact fees and manual payments; run 13 and 14 for parent/student payment flows on separate prepared balances.
  5. Run 15 and 21 for notices and own account. Schedule destructive/password tests after dependent tasks.
  6. Run 16 across roles, including a real 48-hour offline follow-up. Prepare/download while online first.
  7. Run 17 and 18 across roles and physical devices. Run platform packet 19 only with the platform coordinator.
  8. Finish with packet 20 as a paired school-day rehearsal. Record each failed handoff.

Collect reports without losing answers

  • Ask testers for their downloaded report HTML and backup JSON. The optional results CSV is convenient for the tracker.
  • Do not collect only the original checklist file; answers are not written into that original file.
  • Put returned files in returned-reports, with screenshots named by packet, case and tester. Share them through your chosen private channel; the checklist does not upload them.
  • Open a returned report in a browser. It is a readable frozen copy and can be printed/saved as PDF.
  • For another tester or role using the same browser and packet, download the previous report/backup first, then open the backup section and choose Start a new tester response. Otherwise use another browser profile/device.
  • Use the matching backup to continue editing the same feature packet. Browser saving can be restricted on some devices, so downloads are the reliable handoff.
  • Phone browsers differ in support for local HTML. If a phone cannot open it properly, use a computer for the checklist while testing the app on the phone, or print the checklist. Never pretend a blank file contains answers.

Review problems and user experience separately

Use assignment-tracker.csv for ownership/status and problem-register.csv for issues. One issue may affect several cases; keep the same problem number and record all affected cases.

Stop and escalate: another school/family's private data, a duplicate charge, wrong payment totals, lost saved work or access granted without permission. Important: a main task cannot finish. Usability: the task works but needs help, too many clicks or confusing wording. Appearance: clipping, weak readability or unattractive layout.

Ask for four separate ratings: intuitive, easy, beautiful and good overall experience. Yes means it met that description; Partly means only some of it did; No means it did not; Not rated means insufficient use. A working feature can still have poor usability.

Example problem report: Case 12-01. As Bursar on Android Chrome, I opened Fees. I expected to find Record payment near the top. I had to scroll through several sections and needed help. Screenshot 12-01-testerA.png. Suggestion: keep the payment action next to the balance.

Decide whether the release is ready

Record a result for every assigned case. Cannot test and Not tested are outstanding work, not passes. Do not average away a privacy or money failure because appearance scores are good.

  • Access, invitations, student activation and role boundaries must pass for the intended users.
  • Attendance, score entry, result release and A4 printing must complete without manual database repairs.
  • Fees, payments, receipt amounts and retries must reconcile.
  • Prepared offline records must remain usable and queued work must sync safely, including after the actual two-day follow-up.
  • Parent/student tasks must work on a real phone, and serious usability failures must have an agreed fix or explicit release decision.
  • For each remaining problem, record its impact, owner, proposed action and retest date. Obtain the coordinator's explicit release decision.

Features needing a readiness check

Some visible platform screens include local-only/example behaviour. Packet 19 deliberately checks persistence; a success banner alone must not pass. Public-site editing is not currently offered in school Settings, so no tester is asked to find a hidden editor. Legacy PIN screens are not the supported family result route.

React Native and Electron folders are starter foundations. This pack tests the web app and installed PWA; it does not claim finished native app features. Server-only security, backup, email-worker and payment-verification checks remain a developer responsibility, described in IMPLEMENTATION_COVERAGE.md.
